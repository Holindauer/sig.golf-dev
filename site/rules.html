Submission

A submission contains:

  • Four RISC-V programs: keygen, sign, expand, and verify.
  • Three integers: S (signature size in bytes), W (witness size in bytes), and C (verification cycles).
  • Six byte offsets specifying where RISC-V inputs and outputs reside in memory.
  • Lean 4 proofs for every required statement.

Open a pull request against sig.golf-submissions → beta. Follow its submission layout.

Model and costs

All programs and the adversary share a random oracle H. Security counts calls to H. Program budgets and HASH cycles count compressions: hashing n bits costs max(1,⌈n512⌉) compressions.

Required Lean statements

Completeness

Experiment: For any secretKey, message, and oracle H, run keygen(secretKey) to get the public key and cache; sign(secretKey, public key, cache, message) to get the signature; expand(message, public key, signature) to get the witness; then verify(message, public key, witness) to get the verdict. Stop at the first failure. The experiment succeeds when all stages succeed and verification accepts.

KP counts program P's compressions; it is zero if P is never reached. BP denotes P's named budget.

  1. SuccessFor every secret key, PrH[success for every message]≥1−ε.
  2. Compression budgetsFor every secret key and P in {keygen, sign, expand}: 𝔼H,M[2KP/BP]≤2

PrH is over H; 𝔼H,M is over an independently sampled random oracle H and uniform 32-byte message digest M. Attacker-chosen messages or altered caches/signatures may cost more. TODO: Can we improve this?

  1. Verification cyclesFor every secret key, message, and oracle, if the experiment succeeds, verify uses at most C cycles.

Security

Experiment: Let A be a classical probabilistic adversary with unrestricted computation and an integer hash-call budget Q ≥ 1. Sample H and a uniform secret key independently. Initialize an empty transcript T and count every call to H throughout the experiment. Run keygen(secretKey); failure ends the experiment without a win. Otherwise give A the public key and cache.

A may then adaptively query:

random_oracle(input_A)

Return H(input_A).

signing_oracle(message_A, cache_A)

Run sign(secretKey, public key, cache_A, message_A) with the original secret key and public key. Return the signature or failure. Add each returned (message_A, signature) to T. Allow at most L requests.

A makes one final submission in either form:

Witness weak unforgeability

Submit (message_A, witness_A). Win if verify(message_A, public key, witness_A) accepts, no pair in T has message message_A, and the total hash-call count is at most Q.

Signature strong unforgeability

Submit (message_A, signature_A). Win if expand(message_A, public key, signature_A) returns a witness that verify accepts, (message_A, signature_A) is not in T, and the total hash-call count is at most Q.

The total hash-call count includes key generation, signing, A's queries, and final expansion and verification when performed.

Security claimFor every A and Q ≥ 1, over the secret key, H, and A's private randomness: Pr[A wins]≤Q2λ

Program requirements

  1. TerminationEvery program terminates with a result or failure in fewer than T cycles, for every input and oracle.

RISC-V interface

Use RV64I and the M extension. Each program satisfies 4×instruction count+embedded-data bytes<Imax, checked directly at submission.

Code and memory

Code occupies a separate, immutable instruction address space. Instruction i is at 0x1000 + 4 × i. Memory occupies 0x000000–0xFFFFFF (16 MiB), including embedded data, inputs, outputs, scratch space, and stack. The verifier enforces this range directly; it is not a separate Lean proof obligation.

Load D embedded bytes at data_base=16×⌊0x1000000−D16⌋. Initially, sp = data_base and PC = 0x1000; all other integer registers are zero.

Inputs and outputs

Each submission specifies six byte offsets, shared by all four programs: δmessage, δsecret key, δpublic key, δcache, δsignature, δwitness. Each gives the memory address where that object is written or read. The buffers have the sizes in Parameters, start at 8-byte-aligned addresses, do not overlap, and end at or below data_base for every program.

Before each execution, memory is zero except for embedded data and the inputs listed under Programs; unused object buffers remain zero. For example, before sign, write the secret key, public key, cache, and message at their offsets. On success, read the signature at δsignature.

HALT ends execution with a0 = 1 for success, or a0 = 0 for failure. For verify, these mean acceptance and rejection, respectively.

Further details

Proof checking
The certificate must pass Lean's kernel against the organizer's definitions. Its transitive axiom dependencies may contain only propext, Classical.choice, and Quot.sound.
Instructions
Encodings are 32 bits. Fetching outside the code or at a non-4-byte-aligned address fails. FENCE has no effect; EBREAK fails.
Registers
x0–x31 are 64 bits. x0 always reads zero and ignores writes. Aliases are sp = x2, t0 = x5, and a0–a2 = x10–x12. PC is separate.
Memory access
Addresses count bytes; multi-byte integers are little-endian. Loads and stores access only memory, not code. Accesses of 1, 2, 4, or 8 bytes require alignment to their size. Misaligned accesses fail.
Bounds
Every memory access and buffer must fit completely in memory. For unsigned byte address p and length n, require p+n≤0x1000000. All size, layout, and bounds calculations use mathematical integers without overflow. Instruction arithmetic and effective-address calculation follow RV64IM.
HASH arguments
Addresses and bit length n are unsigned 64-bit values. The input's ⌈n8⌉ bytes and the output's 32 bytes must fit entirely in memory; check this before any oracle call or write. Both input and output addresses must be 8-byte aligned.
HASH execution
Read exactly n bits in increasing byte-address order, least-significant bit first within each byte; ignore unused high bits of the final byte. Read all input before writing the answer, so buffers may overlap. Preserve integer registers and advance PC by 4.

Lean project

SigGolf.Certificate submission C in SigGolf/Statements.lean is the competition claim for the exact four program images and declared sizes. SigGolf/Security.lean defines the attacker and both forgery experiments; SigGolf/Riscv.lean defines execution and costs.

Build the statements and regression checks with lake build SigGolf SigGolfTests. Dependencies are pinned in lake-manifest.json. These files define the requirements; they do not certify a particular signature scheme.
